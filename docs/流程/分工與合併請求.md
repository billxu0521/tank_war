# 分工與合併請求（MR）

多人一起做時的規則。合併請求（MR，GitHub 上叫 Pull Request）＝「我在自己的分支做好了，請大家看過再合進 `main`」。

## 基本規則

- **`main` 是大家的起點**：開工從最新的 `main` 開分支，做完開 MR 合回 `main`。不直接推到 `main`
- **一件事一個分支、一個 MR**：一個 MR 只做一件事（一個物件、一個功能、一個修正），比較好審、好退
- 分支名字：
  - `asset/<物件>`：素材（模型、貼圖、音效），例如 `asset/house-porch`
  - `feat/<功能>`：新功能
  - `fix/<問題>`：修 bug
  - `docs/<主題>`：只改文件
- **版號不在 MR 裡改**：`project.godot`、`export_presets.cfg`、`docs/發布/說明.txt` 的版號，發版的人打包時才改（不然每個 MR 都會撞在同一行）
- 合併由 billxu 按

## 素材（模型）的 MR

素材流水線見 [程式建模迭代](../素材流水線/程式建模迭代.md)、[blender/README.md](../../blender/README.md)。

**二進位檔不能合併**：`.glb`、`.png`、`.wav` 兩個人同時改，git 只能二選一，另一個人的就沒了。所以：

1. **開工前認領**：在 [物件表](../素材流水線/物件表.md) 的「進行中」加一列（哪個檔、改什麼、誰、分支）。別人已經登記的檔先別碰，在 DC 講好再接手
2. 改 `blender/<名字>.py`，用 `tools/model_iter.sh <名字> <版號>` 跑，**`.py` 和它匯出的 `.glb` 一起提交**（只交其中一個，下一個人重跑會對不上）
3. 開 MR，先標**草稿**，物件表那列的「MR 狀態」跟著改
4. 下面的檢查都過了，改成**待審**

### 送審前要過的檢查

- [ ] `tools/model_iter.sh` 印 `CHECK OK`（面數預算、零件、葉片卡、反面）
- [ ] 有對照圖（跟參考圖並排），定案的放 `docs/image/final/`
- [ ] `godot --headless --path . --import` 之後，`godot --headless --path . --script tools/asset_budget.gd` 沒有新增超過上限的
- [ ] `godot --headless --script test_battle.gd` 全過
- [ ] 進遊戲看過（`tools/style_iter.sh` 拍一輪，或大廳「檢視模型」）
- [ ] [物件表](../素材流水線/物件表.md) 那個物件的狀態、備註改好

## 程式的 MR

- [ ] `godot --headless --script test_battle.gd` 全過
- [ ] 改到的地方有專門檢查的也跑（根目錄 README 的「開發」那一段列了：連線、槍、農舍……；恐龍走路見 [尼諾拉](../企劃/尼諾拉.md)）
- [ ] 改了數字或行為，對應的文件跟著改（例如 [恐龍行為](../企劃/恐龍行為.md) 寫明「改了程式記得回來改這份」）

## MR 狀態

| 狀態 | 意思 | 誰動 |
|---|---|---|
| 草稿 | 還在做，可以先給人看方向 | 作者 |
| 待審 | 上面的檢查都過了 | 作者 |
| 要修改 | 審的人留了意見 | 審的人 |
| 可合併 | 看過、沒問題 | 審的人 |
| 已合併 | 進 `main` 了；素材的話刪掉物件表「進行中」那列 | 合併的人 |

GitHub 上用「Draft」表示草稿，其他狀態寫在 MR 標題前面，例如 `[待審] asset: 前廊農舍加煙囪`。

## 衝突

- 文字檔（程式、文件）撞到：照 git 的提示合，合完重跑檢查
- 二進位檔撞到：不要合。留 `main` 的版本，在自己分支上**重跑腳本**產生新的 `.glb`（腳本是文字，可以合）
- 場景檔 `levels/ranch.tscn` 是文字但很長，改之前在 DC 說一聲（見 [場景編輯](../素材流水線/場景編輯.md)）
